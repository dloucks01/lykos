# 35 — The chain: vulnerability → PoC → exploit → effect (2026-10-13)

Written because the last two sessions fixed individual links without ever stating the chain, and
a chain nobody has written down is a chain nobody can audit. This is the canonical process the
tool must follow for a binary, a library or a source project, the evidence each link must produce,
and the **measured** status of each. Claims are **[measured]** here or **[observed]** in code.

The rule that governs every link: **a link may not claim more than its evidence supports.** Most
of this project's worst defects were a link reporting success it had not earned — a verified L1
whose bundle did not reproduce, a "corroborated" CVE that was a version match, a 9-second stage
that had built nothing.

---

## The links

### 0. ACQUIRE — what is this thing?

*Produces:* file type, architecture, endianness, bits, mitigations, imports/exports, strings, and
for a source project, an instrumented build.

*Stages:* `ingest`, `ingest_triage`, `source_project.build_source_project`, `unpack`,
`firmware_carve`.

*Status:* **solid for binaries.** 7 formats through one substrate table, 13 ISAs routed to the
right emulator. **Source projects were the weak link and are now better:** builds are linked
static so the tools are self-contained ELFs rather than libtool wrapper scripts needing a
`.so` nothing stages **[measured]**, and up to 6 of the executables a project builds are
registered instead of only the largest **[observed]**.

*Known gap:* a pristine tree whose config header is generated by `configure` is not configured
before the in-process harness build, so the harness cannot compile **[measured]**.

### 1. REACH — get execution into the code that can be wrong

*Produces:* an input channel, a valid-shaped seed corpus, and executions **inside** the parser.

*Stages:* `invocation.propose_argv`, `capture.modes_for`, `fuzz/structure` (format models +
per-codec seeds), `fuzz/textconf`, `fuzz/menu` (menu + linear prompt protocols), `libfuzzer`
(in-process).

*Status:* **this is where the tool was weakest and where today's gain is.** Measured on libtiff
4.0.3: external file-channel fuzzing 14,821 executions at 42.1/s and **zero** crashes; the same
library in-process at **3,780/s**, and a CWE-125 heap-buffer-overflow in libtiff's own
`gtStripContig` allocation found in **20 executions** **[measured]**. The seed that triggers it is
the SGILog per-codec seed, with no mutation at all **[measured]** — before per-codec seeding every
input decoded with `Compression=1` and no codec was entered.

**One harness per library is closed (2026-10-14).** `plan_harnesses` ranks every door into a
tree — the harnesses the project itself ships, a known-library harness, each
create → consume → destroy triple, then single-function picks — and the autopilot fuzzes the
strongest with a full slice, then takes the rest in a second pass. Four things had to be true
before breadth was worth having rather than a way to spend budget on nothing:

  * **a file-backed handle harness** (`synth_file_handle_harness`). The dominant shape in a
    format library is `TIFFOpen(path, "r")` → `TIFFReadEncodedStrip(tif, strip, buf, size)`,
    where the bytes come from the FILE and `buf` is where the decoded image is written to.
    Synthesized the other way round, the constructor gets NULL for the filename and every
    execution returns at `if (!h)`. Which way round is decided by the constructor
    (`ctor_opens_a_file`: named like an opener AND taking a string), because that is where the
    evidence is.
  * **one compile, many harnesses** (`BuildCache`). Each harness LINKS objects the first build
    compiled: measured 13.4 s for libtiff's first harness and **0.5 s** for each of the next
    five **[measured]**. Without it, breadth would cost depth for no reason.
  * **candidates that can actually be called.** A multi-line `static` (expat writes the storage
    class above the name), a function in a translation unit with `main`, a platform port's file,
    an allocator whose `(void *, size_t)` looks exactly like a buffer pair, the project's own
    harness symbol, and a non-const `void *` first parameter — which is an OUT parameter, so
    feeding it the fuzz bytes earns a heap-buffer-overflow WRITE in the library's own code that
    is entirely our doing. Every one of those was a candidate the ranking used to offer.
  * **C read the way it is actually written.** zlib 1.2.11 defeated the scanner four separate
    ways at once: K&R definitions (`int uncompress (dest, destLen, source, sourceLen)` with the
    types below), `#define local static` so nothing is spelled `static`, `voidp` for the buffer
    parameter so no `*` appears in it, and `gzopen OF((const char *, const char *))` in the
    header so the declared name reads as `OF`. `_fn_defs` found **zero** functions in
    `uncompr.c`, `gzlib.c` and `gzread.c` **[measured]**.

**Breadth multiplies the cost of a wrong harness, and that is the real risk here.** Teaching the
PLANNER to read K&R while `fn_params` kept its own ANSI-only copy of the same regex produced a
harness that declared `void gzopen(char *)` and called the real two-parameter
`gzopen(path, mode)` with one argument: `mode` was whatever was in the register, zlib
dereferenced it, and the campaign reported **an ASan SEGV in zlib on execution one**. A
fabricated crash in a real library is the worst thing this tool can emit — it is indistinguishable
from a finding until someone reads the stack. There is now ONE definition scanner (`defs_index`)
feeding the plan, the shape inference and the call, because three copies of one regex is how that
happened. The same reasoning is why a harness frees its output buffer only after the handle is
closed (a reader may keep it), and why an `oom-` artifact is filed as CWE-400 and not as the
CWE-787 that a "crash under libFuzzer" default would have made of it.

Measured end to end through the autopilot, 600 s per target, same corpus and budget as the
morning's run **[measured]**:

| library | doors | executions | crashes | demonstrated | before |
|---|---|---|---|---|---|
| libtiff 4.0.3 | **6/6** | 190,666 | **3** | **6** | 1 door, 10,969 execs, 1 crash, 2 demonstrated |
| zlib 1.2.11 | **4/6** | 5,958,887 | 0 | 0 | 1 door, 9,802 execs |
| expat 2.1.0 | 1/1 | 15,031 | 1 | 2 | 1 door, 2,501 execs |
| bzip2 1.0.6 | 1/1 | 463,676 | 0 | 0 | 1 door, 28,786 execs |

libtiff's two extra defects are the UBSan faults behind `TIFFReadEncodedStrip` and
`TIFFReadRawStrip`. zlib's best door is `gzopen` → `gzread` → `gzclose` (cov 407 against 293 for
the known harness **[measured]**); the two doors it did not open were the budget's decision, and
the row says so rather than implying they were tried. The execution counts are not comparable to
the morning's in kind as well as in size: libFuzzer's own count was never read before, so a
library's in-process work was simply absent from the total.

Three UBSan faults in libtiff behind doors the single harness never opened **[measured]**:
`tif_read.c:460` and `tif_read.c:545` (reached only through `TIFFReadRawStrip` /
`TIFFReadEncodedStrip`) and `tif_dirread.c:3766`.

*Honest limit:* a door is only synthesizable where the signature says enough. expat's second
entry (`XML_GetBuffer` + `XML_ParseBuffer`) needs the caller to copy into a buffer the library
hands back, and bzip2's streaming API passes everything inside a `bz_stream`; neither can be
filled from a signature. bzip2 also spells its definitions `int BZ_API(BZ2_bzBuffToBuffDecompress)
(char* dest, ...)`, where the macro wraps the NAME — readable, but its input is parameter 3 and
its first parameter is an output buffer, so synthesizing a call would hand the fuzz bytes to the
wrong argument and fabricate a crash. Those two keep their `_KNOWN_HARNESSES` entry, which is
per-library knowledge gated on the symbols being present. No `-dict=` is built from the library's
own strings.

### 2. OBSERVE — notice that it went wrong

*Produces:* a fault with a class: a signal, a sanitizer report, or an oracle verdict.

*Stages:* `sandbox.run` (signals), ASan/UBSan/MSan/TSan builds, `mem_oracle` (uninitialised
reads, which never fault), `heap_check`, `monitor`, `libfuzzer`.

*Status:* **solid, with one defect fixed today that invalidated the links after it.** A
sanitizer-detected fault exits with a CODE, not a signal, so `crashed` — which asks "was it killed
by a signal" — was False for a real heap-buffer-overflow, and the PoC was filed unverified
**[measured]**. The verification path now reads the sanitizer report through
`parse_asan_report`, which already separates a true report from a sanitizer SETUP failure.

### 3. ATTRIBUTE — say what the defect is

*Produces:* a CWE, a source location where available, a root cause, a dedup key.

*Stages:* `root_cause`, `debug/rootcause.parse_asan_report`, `detect_cwe`, `cve_fingerprint`.

*Defect found by the regression benchmark on its FIRST real run (2026-10-15), and fixed:* **a
sanitizer defect was attributed to the machinery that reported it.** The site came from "the first
stack frame naming a real source file", and on a build that halts on error there is no such frame
in the library: UBSan aborts, libFuzzer catches the deadly signal and prints ITS stack, and glibc
ships source names — so expat's real left-shift fault was recorded as `pthread_kill.c:43`, the file
`abort()` raises from **[measured]**. ASan was wrong the same way one frame earlier, through its own
`compiler-rt/.../asan_interceptors*.cpp`. This is not a cosmetic label: **the site is the dedup key
for a sanitizer defect** (`libfuzzer:<site>`), so every UBSan fault in a campaign collapsed into one
finding at one glibc line — which is exactly how three UBSan sites in libtiff can become one. UBSan
now answers with its own `runtime error:` location, which is authoritative, and the stack walk skips
the sanitizer runtimes, libFuzzer's driver and the libc raise path.

*And one more, from the same run:* a `site_detail` without an ADDRESS recorded no site at all
(`finding_site` was written only when `function_addr` or `site_addr` was set). A sanitizer defect in
a source build has no address — it *is* `file:line` — so every in-process library finding carried its
location only inside an evidence sentence, where the report, the UI and the benchmark all read it as
empty **[measured]**.

*Status:* **works, with one standing honesty problem.** `cve_fingerprint` is VERSION MATCHING:
108 CVEs on libtiff 4.0.3, 54 on expat 2.1.0, none of them reached **[measured]**. It files as
`corroborated`, which reads like evidence about this binary. It needs its own tier saying "this
build contains the vulnerable version; we did not reach it here". Until then the report's
`demonstrated` vs `detected` split is the only thing keeping it honest.

### 4. REPRODUCE — prove it outside the pipeline

*Produces:* a verified PoC and a bundle that reproduces on a machine that is not ours.

*Stages:* `build_poc`, `poc/bundle`.

*Status:* **solid and now gate-enforced.** The bundle is unpacked into a fresh directory and its
own `runner.sh` is executed by the conformance gate on 5 channels (argv/file/env/socket/prompt),
with a negative control proving the check fails when the reproducer is broken **[measured]**.
Three defects lived in this link until today: a prompt-protocol crash could not be replayed, the
bundled reproducer delivered in bulk, and `runner.sh` ended on `echo` so **every bundle ever
shipped exited 0** whether the reproducer crashed or ran clean **[measured]**.

*The rule this link earned:* test a reproducer by EXECUTING it and reading its STATUS, never by
reading what it prints.

### 5. PRIMITIVE — say what the defect gives an attacker

*Produces:* instruction-pointer control, a write-what-where, an OOB index, a leak — with the
offset and the confirmation.

*Stages:* `poc_primitive`, `chain_primitive`, `heap_trace`/`heap_search`.

*Status:* **closed for out-of-bounds accesses (2026-10-14); still CTF-shaped for the rest.** Every
demonstrated L2 before this came from a stack overflow with a reachable saved return address. A heap
OOB READ in a decoder — the class the in-process engine finds — yields no IP control, and the stage
had no way to say what it DOES yield, so it reported "crash reproduced but no instruction-pointer /
memory primitive found": technically true and completely empty.

Three defects were behind that, each found by pointing the stage at a clang ASan build of a one-line
out-of-bounds read:

- **The fault was invisible.** ASan does not die on a signal by default — it prints its report and
  calls `_exit(1)` — so the ptrace capture saw a program that ran and exited cleanly and the stage
  declined with "cyclic pattern did not fault via any of stdin, file, arg". No L2 was reachable on
  *any* sanitizer build, which is every target the source-code path compiles. The capture now
  exports `abort_on_error=1`.
- **A read was reported as a write.** `heap-buffer-overflow` is ASan's name for a one-byte read past
  the end and for a wild write alike, and both resolved to CWE-122 at severity *critical*. The
  report states the direction, so the class is resolved by it: read → CWE-125/high, write →
  CWE-122/critical.
- **The two stages disagreed about the target.** `build_poc` replayed a libFuzzer crash against the
  harness it was found in; `poc_primitive` staged the *ingested* binary, detonated a tool that never
  calls the vulnerable path, and reported no primitive for a defect it had never reached. The
  lookup is now one shared function.

*What the verdict is:* step 2b asks the question that separates a bug from a primitive — does the
attacker choose how far out of bounds the access goes? — by varying the input and watching the
distance past the end of the object. A distance that moves is a confirmed `controlled-oob-read` and
an L2; a fixed distance is an `oob-read` reported as unproven. The bundle ships the variant table,
so the claim is auditable rather than asserted, and exports `abort_on_error` itself — without that
the operator gets exit 1 where the README promises 134 and concludes the PoC is broken.

**Lifetime defects closed (2026-10-15).** The distance experiment genuinely does not apply to a
dead object: a use-after-free's distance is an offset INSIDE a freed chunk, and a double free has
no access to measure at all. So both classes ran the whole ladder and reported "crash reproduced
but no instruction-pointer / memory primitive found" on every sanitizer build — the same empty
verdict an out-of-bounds read used to get. Step 2c asks the two questions that DO decide whether a
lifetime defect is a primitive, and the report answers both:

  * **which part of the dead object is touched** — the offset inside the freed chunk. If it tracks
    the input, the attacker picks which FIELD of whatever reclaims the chunk is read or written: a
    function pointer, a length, a reference count.
  * **how big the dead chunk is** — the region size. If that tracks the input, the attacker picks
    the SIZE CLASS the dangling pointer lands in, which is the grooming step every use-after-free
    exploit and every tcache-dup double free needs.

Either one moving is an L2 (`controlled-uaf-read/write`, `controlled-double-free`); neither moving
is the defect reported as unproven, exactly as for out-of-bounds. Measured end to end on clang ASan
builds: a use-after-free read whose offset the first input byte picks reaches a **verified L2** with
CWE-416 and a bundle that reproduces at exit 134, and a double free whose chunk size the input picks
reaches a verified PoC with CWE-415 **[measured]**.

*What step 2c does NOT claim, said in the effect text and in the bundle:* ASan holds the freed
chunk in quarantine — that is HOW the use is caught — so nothing reclaimed it during that
experiment and no overwrite of a live object was demonstrated there. The claim is that the defect
is attacker-parameterised.

**The reclaim experiment (2026-10-15).** The quarantine is the reason step 2c stops where it does,
and the reason the other half has to be shown somewhere else: on a build WITHOUT a sanitizer the
allocator behaves normally, and the target's own output is the oracle. `heap_uaf_reclaim` drives

    add(victim, S)  add(guard, S)  free(victim)  add(attacker, S, MARKER)  view(victim)

and the question becomes one bit: does the view of the FREED entry print the marker the LATER
allocation carried? If it does, the attacker's bytes occupy the chunk the stale pointer addresses
and the program read them back through it — reclaim, controlled contents and a use, each observed
rather than modelled. `groom_reclaim` had the RECIPE for this since the heap-model work and no
caller; this is the demonstration.

Two guards make it evidence rather than a story:

  * **the control run.** The same sequence with the attacker's allocation in a different size
    class, where no reclaim is possible. A target that echoes recent input out of a shared buffer
    would print the marker whatever the allocator did; if the control prints it too, the oracle is
    unsound here and the verdict is `reclaim-inconclusive` — reported, filed as nothing, and not
    counted. The marker is all digits because a menu that case-folds stored text mangles letters,
    which is what `identify_heap_ops` already learned probing for the view option.
  * **the nulled-slot control, in the suite.** The same notebook with `free` nulling the slot
    reclaims the chunk just as readily and must demonstrate NOTHING, because the defect is the
    stale pointer and not the reuse. A verdict driven by "did the allocator hand the address back"
    would fire on code with no defect **[measured]**.

Measured end to end on a plain `gcc -O0` notebook: `controlled-reclaim` at size 0x80, the marker
returned through the freed entry and absent from the control run, filed as a CWE-416 finding
carrying a DEMONSTRATED memory-corruption effect **[measured]** — and absent on the nulled-slot
build **[measured]**. The claim stops where the evidence does: *what the program then does with
those bytes is not shown — a function pointer among them would be a hijack, and that is the
exploit stage's claim to make.*

The conformance notebook (`heap_uaf_read`) now carries TWO `heap_trace` CWE-416 findings where it
carried one — the disclosure and the reclaim — which is the autopilot-level evidence that the
experiment runs where it should and not only in its own test **[measured]**.

**The classes that state a MAGNITUDE and no access (2026-10-15).** Steps 2b and 2c cover the
classes that describe memory. A third family describes neither: a 35 TB allocation request, a
leak, a negative length handed to `memcpy`, an out-of-bounds index. Nothing went past the end of
an object and nothing died, so both verdicts declined and the ladder ended on *"crash reproduced
but no instruction-pointer / memory primitive found"* — which for a refused allocation is not a
near miss, it is an answer to a question nobody asked about this defect. Step 2d asks the one the
report can answer: it states a NUMBER (the size requested, the bytes leaked, the index used, the
shift applied), and the same vary-the-input experiment says whether the attacker picks it.

**This verdict can never reach L2, whatever the experiment shows.** L2 means a confirmed
exploitation primitive; an attacker-chosen allocation size is an availability defect. The verdict
declares its own ceiling (`max_level`) and `_finalize` honours it, because calling a controlled
denial of service an exploitation primitive would inflate the single number in a report that
exists to resist inflation. The same honesty runs through the effect STATUS: a refused allocation
really was requested and a leak really did leak, so those are `demonstrated`; a negative length was
intercepted *before* the copy and an out-of-bounds index is undefined rather than performed, so
those go in as `potential` with their magnitude recorded — what a build without the sanitizer would
do is an inference, and an inference is not a demonstration.

*The defect that was in the way, and it is the worst kind:* ASan states this class as a SENTENCE —
`requested allocation size 0x800000000000 ... exceeds maximum supported size of 0x10000000000` —
so the class regex took `requested`, which is in the non-bug denylist, so `parse_asan_report`
returned **None and the entire report was dropped** **[measured]**. Not mislabelled: *absent*. A
reachable, CVE-bearing class (libtiff and libjpeg both carry CVEs for exactly it) produced no
finding of any kind, while the `allocation-size-too-big` entry meant to label it sat in the table
unreachable — the very outcome its own comment claims to have fixed. Sentence-worded classes are
one table now (`_ASAN_SENTENCE`), which is where the double-free sentence found earlier in the day
also lives.

**The concurrency verdict (2026-10-15).** Every verdict above varies the INPUT and watches a
number move. A race's outcome does not depend on the bytes at all, which is why the stage declined
the whole family by name — *"its exploitability is a TIMING property; varying the input cannot show
it, and this stage only varies the input"*. The premise was right and the conclusion was not: a
concurrency defect has a property that needs no input variation, and it is the one whoever acts on
the finding needs. **Does the same input fault every time, or only sometimes, and how often?**

Step 2e detonates the same bytes `RACE_RUNS` (8) times and reports the rate. A defect seen on 1 run
in 8 is real and needs retries; one seen on 8 of 8 is reliable *in this harness*, which is a fact
about the harness and not a guarantee about another machine. And a fault that reproduces on none of
the repeats is the most important of the three to say out loud, because the alternative is a
single-shot reproducer the operator runs once, sees nothing from, and writes off — the "verified L1
whose bundle did not reproduce" failure this document opens with.

So **the bundle loops**. `runner.sh` for a race makes the number of attempts the measured rate
justifies (three expected hits, capped), stops at the first run that prints the detector's own
report line — not on an exit code, which belongs to the detector and which plenty of other things
set — and when it never reproduces it says so and exits non-zero. Like every other verdict here it
is capped at L1: nothing about a race controls memory or execution, and what the race CAUSES
depends on what the unsynchronised value is used for, which this stage does not determine.

**Window widening (2026-10-15).** The rate answers "how often"; the next question is whether the
attacker can RAISE it, because that is the difference between a defect and a tool. A 1-in-8 race is
a curiosity to whoever has to reproduce it; the same defect at 6-of-6 is usable. Widening the
window is how that is done in practice — a longer input to parse, a larger count to iterate — so
the experiment measures a RATE per input variant rather than asking whether one run reported.

The comparison is an exact one-sided binomial tail, not two fractions weighed by eye: if the defect
really reports at the baseline rate, how surprising is this variant's count? 6-of-6 against 1-in-8
has a 3.8e-06 chance of arising; 2-of-6 has a 17% chance and is called nothing. The threshold is
stated (`WIDEN_ALPHA` 0.05) rather than tuned, and the effect text carries the caveat the sample
size demands: the baseline is itself an 8-sample estimate, so this is a directional result and not
a published p-value.

Two things follow from it. **The bundle ships the input that makes the defect reliable** — a
reproducer for a 1-in-8 race should not be the 1-in-8 input when a 6-of-6 one is in hand — and the
attempt count drops with it (3 attempts, not 24). And the experiment runs **only on an intermittent
defect**: a race that already reports every run has no window left to widen, and measuring a rate
costs a process per run, so the most expensive experiment in this stage is spent only where its
answer can change what the operator does. A widening that was attempted and found nothing is
printed with its variants, because the alternative is a reader who cannot tell it from an
experiment nobody ran.

*Tested with the detonator injected*, since a fixture that reports intermittently ON PURPOSE is a
flaky test and the flakiness is the thing under test: one case proves the widening is found and
the widened bytes are handed to the bundle, another proves a reliable defect spends exactly
`RACE_RUNS` runs and no more.

*Three defects were in the way, each measured.* A race has no single site — two accesses collide —
and the report named NONE of them, because TSan writes `#0 bump /src/race.c:6:66 (race+0xea472)`
where ASan writes `#1 0x5a in main /src/x.c:12`: no address, no `in`, so the frame pattern matched
nothing and a data race had no source location at all. `parse_asan_report` never set the
`sanitizer` field that `libfuzzer_stage` reads with a default of `"AddressSanitizer"`, so every
UBSan and TSan finding ever filed claimed ASan in its evidence — and that field is also the only
honest way to tell TSan's `heap-use-after-free` from ASan's, which share a class name and share no
evidence. And the ptrace capture saw no fault at all on a TSan build that does not carry our own
`__tsan_default_options` hook, because TSan's default is to report and carry on: the capture now
exports `halt_on_error=1:abort_on_error=1` for TSan and UBSan as it already did for ASan.

*And one the suite found, in my own fix:* recording the run assumed `ctx.run_id`, the helper is
called with a test double that has none, and the enclosing `except: continue` swallowed the
AttributeError — discarding a race it had already filed. The bookkeeping is recorded separately
now, after the count, so a defect in it cannot retract a finding, and a failure to record says so
in an event instead of vanishing.

*And the one the conformance gate found:* `tsan_detonate` filed a `corroborated` FINDING and
recorded no RUN, so a real data race reached the report and **nothing downstream ever touched it**
— no PoC, no rate, no looping reproducer. The libFuzzer stage had exactly this defect and its own
comment says the same thing: record it as a run, or the ladder cannot see it. The shared
replay-target lookup (`replay_exe_for`, renamed from `libfuzzer_harness` because it answers a
wider question now) resolves a `tsan` isolation to the ThreadSanitizer build, since replaying a
race against the ingested ASan binary is not a weaker test but one that cannot report a race at
all. Measured end to end on a source drop: a `CWE-362` finding, a dyn_result row the prove loop
can see, and a verdict carrying its rate.

*The gate case itself could not stay.* A data-race case needs a TSan build, which exists only for
a SOURCE drop, and every case in `pipeline_conformance.py` compiles its fixture and ingests the
BINARY. The case found the gap, the gap is fixed, and the assertion lives in the suite where
source can actually be ingested — the gate keeps no red case, and the limit is recorded here
instead: **the conformance gate cannot cover a sanitizer-variant class.**

*And a cost nobody had counted:* each of the three verdicts detonated the original input itself to
decide whether it applied, and so did the decline — four sandbox runs of the same bytes before a
single VARIANT was tried, out of a budget that buys ten. One detonation now feeds all four.

*And one more thing a class with no verdict now gets:* a REASON. A ThreadSanitizer data race and an
MSan uninitialised read both ended on the generic note, which reads as if the right question had
been asked and answered — so the reader goes looking for a missing capability instead of at
`mem_oracle` (whose verdict the uninit disclosure is) or at a timing experiment this stage does not
run. `no_verdict_reason` names the class and says why there is nothing to say.

**The reclaim oracle for a target with no output (2026-10-15).** The experiment above needs a
`view` option to read the stale entry back, and most targets have none — a service, a parser, a
tool that prints nothing from its heap. For those, the only reclaim evidence was the tracer's "the
chunk came back", which says nothing about whose bytes are in it.

The ptrace tracer can read the tracee's memory, so it is the oracle: it samples the chunk **twice**
— once when it is freed, where the marker must NOT already be present, and again after a later
allocation is handed the same address. Marker absent before, present after, and the attacker's
bytes are in a chunk a stale pointer still addresses. That before/after pair is a *stricter* control
than the output route can offer: a program that echoes recent input cannot fool a read of the chunk
itself, and an observation where the marker was already there is refused rather than reported with
a caveat.

The claim is weaker in one specific way and the text says so: the output route shows the program
READING the attacker's bytes back through the stale pointer, and this one shows only that the bytes
are there. Both are reclaim; only one of them includes a use.

**The reading half (2026-10-15).** The oracle above shows the attacker's bytes sitting in the dead
object. It does not show the program TOUCHING them, and on a target with no output path there was
no way to — so the verdict carried the caveat and stopped. The tracer can close it: it already
arms a hardware watchpoint on a freed chunk's data for the classic use-after-free, and the same
mechanism answers this question if it is armed at the right moment.

The right moment is **the instant the marker is confirmed**, and that is what makes the
observation unambiguous. By then the reclaiming owner's fill has already happened, so any later
read of that chunk from the program's own code cannot be the filler — it is a read of the
attacker's bytes through a pointer the program should have stopped using. It is reported under its
own name (`reclaim-use`), because "read memory that now belongs to another object" is a different
fact from the classic "touched memory that is FREE", and the same conservatism applies: the
target's own code only, never the allocator's bookkeeping.

The sequence had to grow a tail for it. Nothing in the earlier shape touched the victim's index
after the reclaim, so there was nothing for the watch to see; it now drives every OTHER
index-taking option against the victim, and whichever one consumes a stored object reads the
attacker's bytes. An option that does something else costs a few writes; one that frees the chunk
again is a double free the tracer reports anyway.

So three facts are now separable, and the finding says which it has: **the chunk came back**, **the
attacker's bytes are in it**, and **the program read them** — the last one naming the pc. Measured
on a notebook with no printing path whose `sum` option folds a stored object into a global: the
finding reads "attacker bytes reclaimed AND read (traced)", and the effect text keeps exactly one
caveat, which is the honest one — what the program DOES with the value is still not shown, and a
function pointer among those bytes would be a hijack the exploit stage has to claim.

**The consumer effect (2026-10-15).** The reading half shows the attacker's bytes reaching a
consumer. The last question is what the consumer DOES with them, and the marker answers it without
any new machinery: eight ASCII digits are also a machine WORD, so the marker is already a sentinel.
If the program calls through the value it read, the control transfer goes to the attacker's bytes;
if it dereferences it, the fault address is those bytes. The tracer classifies the fault instead of
inferring a mechanism from the signal — `control-flow-hijack`, `dereference`, or plain `fault` when
it is neither, which claims nothing.

*And the sentinel taught a lesson worth writing down.* Eight printable bytes can never have zero
top bytes, so the value is a **non-canonical** address — and a jump to one raises #GP, not a page
fault. The kernel reports #GP as SIGSEGV with **si_addr 0 and the pc still ON the faulting
instruction**, so neither "the pc is our bytes" nor "the fault address is our bytes" can fire, and
the hijack looks like an unexplained fault **[measured: pc at the `call`, si_addr 0, while the
chunk still held the marker]**. The evidence in that case is one step inward: the faulting
instruction is an indirect call/jump (`FF /2`../5, REX prefixes skipped) and a general-purpose
register holds the attacker's bytes. Measured on a notebook whose object begins with a callback:
`call *%rax` with the marker in `rax`, reported as a hijack naming the register.

So the finding headlines a **demonstrated control-flow hijack** with RCE as POTENTIAL — the same
split `poc_primitive` uses for an L2 IP-control primitive, and for the same reason: the flow is
hijacked, no attacker code has run, and here the landing address faults immediately by
construction. Four observations, none inferred: the chunk came back, the bytes are the attacker's,
the program read them, and it called through them.

**Code execution (2026-10-15).** Everything above answers *what is true of memory*; this answers
*so what*. The hijack stops at a fault because the sentinel is deliberately unmappable, so the
experiment is to substitute a REAL address in bytes already shown to be attacker-chosen and
breakpoint it: the program either arrives at the chosen function or it does not.

The target comes from `exploit.find_win`, reused rather than re-invented, and its strictness is
the point — its own comment says that redirecting into a function the program calls anyway is a
much weaker claim than the badge implies. No win function, no claim, and the hijack stands on its
own. The address needs the load base, so the tracer now reports where the image landed; the stage
builds `base + vaddr` into the reclaim payload at the offset the hijack evidence named, and the
tracer breakpoints the function. Arrival is observed at that breakpoint, never inferred from the
absence of a crash.

Measured end to end on the callback notebook with a `win` that writes a line: the finding reads
*"reclaimed object redirects execution into win"* and files **rce: demonstrated** beside the
hijack. **Five observations, none inferred** — the chunk came back, the bytes are the attacker's,
the program read them, it called through them, and it arrived at code of our choosing.

*One limit travels with the claim, in the effect text and in the report:* the function is one the
binary already contains, so this is a redirect and not injected code.

**Wired to the leak (2026-10-15).** The other limit — the address being knowable only because the
tracer disables ASLR — is gone where the target discloses enough to remove it. `classify_leak`
already recovers the IMAGE base from the binary's own symbols, and `heap_uaf_leak` was **throwing
it away**: the number a redirect needs was computed and dropped, which is the same shape as the
tracer discarding the reclaim and the leak path keeping only its libc answer. It is kept on every
return path now, and a run that recovers only the image base is an answer rather than a miss.

Two further defects sat behind it, both measured. The leak's *hit* never reached the exec
experiment — `_try_uaf_leak` returns a metrics dict, so `leak.get("pie_base")` was quietly `None`
and the chain reported *"no disclosure here recovered the image base"* while the function that
said so had the base in hand. And the libc strategies win first, so their dumps are full of libc
pointers: a target that discloses its own code pointers still came back with `pie_base: None`
until one extra drive of the small-chunk view — the dump that shows the OBJECT's bytes — was made
lazily, only when the image base is still unknown.

The exec payload now prefers the leaked base and **cross-checks it against the base the tracer
measured**, because two independent routes to one number is the only way to show the leaked one is
right rather than merely present. Measured end to end: *"the address of `win` (0x5555555551d0,
from leaked at runtime) … the leaked image base matches the one the tracer measured
(0x555555554000), so the address does not depend on ASLR being off"*. Where no disclosure yields
the base, the old caveat is printed instead — and the stage says which of the two it has.

*Three things had to be fixed to make it work, each measured.* The reclaim-provoking op sequence
existed only in the STATIC fallback generator, so it was never driven against a target whose menu
crawl succeeded — which is most of them; it is built from the crawled model now, with typed fields,
exactly as the output route's is. The sequence had to gain a trailing allocation whose only job is
to give the tracer a stop AFTER the fill: the fill is the `read()` that follows the reclaiming
`malloc`, and a sequence ending at that malloc leaves nowhere to look, because by the end of the
run the tracee has exited and its memory cannot be read. And `pie` — which decides whether every
breakpoint is rebased to the load base — comes from TRIAGE, so a `heap_trace` that runs before it
read `pie=False` for a PIE binary and mis-placed every breakpoint: **22 sequences driven, not one
alloc or free event, reported as "no heap primitive surfaced"**. A clean bill of health from a
tracer that never stopped anywhere is the worst shape a false negative can take, so the ELF header
answers when the row cannot.

*And the tracer's half, for a target with no `view` option and so no oracle:* `heaptrace` already
computed the reclaim and threw it away — `freed.discard(ptr)` on an allocation return IS the
freed chunk being handed back out — so the one observation that turns a lifetime defect into a
controllable one was derived and discarded on every run. It is now recorded (as an `event`, never
an `error`, so nothing that scans for faults can mistake it for one), and the op-sequence
generator gained the free-then-same-size-allocate shape that provokes it, which nothing in the
sequence set did before.

*Three defects in the evidence were in the way, each measured:* the lifetime region wording is
`located 5 bytes inside of 128-byte region` — with an `of` the overflow wording does not have — so
every use-after-free reported **no offset and no chunk size** — the two numbers this verdict turns
on. A free-side defect states its class as a SENTENCE (`attempting double-free on 0x...`), so the
class regex took the first token and a double free went out as class `attempting` with **CWE-119**,
a generic corruption label, while its own CWE-415 sat two lines below in the same table. And a
lifetime defect has THREE locations — the use, the free and the allocation — of which the report
named only the use, which is the one thing the stack trace already showed the reader.

*And the last class in this stage with no verdict of its own: `use-of-uninitialized-value`.* It
was declined by name, on the grounds that an uninitialised read is only a disclosure if the value
reaches an output and that `mem_oracle` already draws that line. True about the line, wrong about
the owner — twice over. MemorySanitizer draws it too, in the report this stage already holds; and
`mem_oracle` is a bounded triage pass over inputs it picks for itself, so *"some run of this
program discloses"* and *"THIS input discloses"* are different claims and only the second one can
carry a bundle.

The class is one name for two defects an operator must triage differently, and the report tells
them apart. `Uninitialized bytes in write at offset 0 inside [0x7ffe…, 128)` is printed only when
the undefined bytes reached an INTERCEPTOR — that is CWE-200, stack or heap residue out of the
process, observed rather than inferred — and its absence is the internal half, CWE-457, where the
value was merely used. Nothing was reading that line, so a branch on a stale flag and 128 bytes of
a dead frame going out on a file descriptor were filed under one title, one CWE and one severity.
It is also printed **before** the `WARNING:` line, so a parser that reads the text after the
warning finds no escape and files every disclosure as an internal read. Origin tracking supplies
the other half: `created by an allocation of 'b' in the stack frame` vs `by a heap allocation`,
with the origin's own site — **not** the use site, because the line to change is the one that
declared or allocated without an initialiser, and the use site is the one thing the stack trace
already shows.

*The experiment this class actually turns on is not a variation but a look at the bytes.* MSan says
a value was undefined and that it reached an output; both halves are about the defect, and the
consequence is decided entirely by what happened to be in that memory. A dead frame holding 128
zeroes is a bug to fix; the same frame holding the previous call's input buffer is a primitive. So
`residue_verdict` plants a distinctive marker in the input and looks for it in the program's own
output — the uninitialised-memory analogue of the reclaim experiment, where the question was
whether the attacker owns the contents of a freed chunk and here is whether they own the contents
of memory that was never written at all. Four outcomes, strongest first: `input` (the marker came
back), `pointer` (the bytes corroborate an image base, via the same `classify_leak` the exploit
stage consumes), `filled`, `unknown`.

That experiment is only possible because of a measured fact: **MSan's interceptor reports the
undefined bytes and then performs the write**, so the residue it is complaining about is on the
same run's stdout. Were it not so, answering "whose bytes" would need an uninstrumented build, and
for a source drop the pipeline has none — it builds ASan, MSan and TSan and no plain binary. Which
matters more than it sounds, because the `filled` outcome exists for a reason that was measured
first: **on the ASan build a fresh frame reads as zeroes and a fresh heap allocation as `0xbe`**
(`malloc_fill_byte`), so a residue verdict taken from that binary would be measuring the sanitizer
and not the program. The check comes before the other two, so an all-zero block is never read as a
null pointer, and the honest answer survives being run on the wrong build — it just stops being
informative.

Levels: an escape whose bytes are shown to be the attacker's (or to carry an image base) may reach
L2, the standing the out-of-bounds and use-after-free READ verdicts already have for the same
reason — memory the program did not intend to expose, reaching an output, with the content
accounted for. An escape whose residue is unrecognised stops at L1: bytes left and what they were
is not shown. A value that never escaped stops at L1 whatever the experiment says.

*Two defects in the plumbing were in the way, and the first of them is one this document has
already recorded once.* `msan_detonate` filed a `corroborated` FINDING and recorded **no run** —
and the prove loop iterates `dyn_result`, so a real uninitialised-memory disclosure reached the
report and nothing downstream ever touched it: no bundle, no volume, no verdict on whose bytes
escaped. `tsan_detonate` had exactly this defect, the libFuzzer stage had it before that, and its
own comment says the same thing. The isolation tag has to name the MSAN build, because no other
build reports this class and the ASan one destroys the evidence. And the severity was coming from
the SIGNAL: MSan halts the process, `_SIG_CWE["SIGABRT"]` rates that `high`, so the half of the
class where nothing left the process went out at the same severity as a demonstrated disclosure —
the substrate deciding the severity instead of the defect, which is the complaint written out in
full beside the PE exceptions in that same table.

*A limit this verdict respects rather than papers over:* the escape half sees output calls MSan
INTERCEPTS. A disclosure laundered through uninstrumented libc formatting — `printf("%.64s",
uninit)` — loses its shadow inside libc and MSan stays silent on it at every `-O` level, although
it visibly prints the previous frame's bytes. That shape is `mem_oracle`'s (valgrind's shadow
memory sees the read itself), and the two gate cases now say so to each other: `src_uninit_read`
for the branch-on-undefined shape and `src_uninit_disclosure` for the intercepted-write one.

*And the note that said this could not be gated was too broad.* It read "the conformance gate
cannot cover a sanitizer-variant class: every case there compiles its fixture and ingests the
BINARY, while TSan/MSan builds exist only for a source drop". The second half is true of the
FUZZ-pass route and not of the verdict: `as_source=True` ingests source, the platform builds MSan
itself, and `src_uninit_disclosure` now drives the whole chain through the real autopilot —
reported, recorded as a run, replayed against the MSan build, escape measured, marker planted,
L2 earned by the residue and by nothing else.

## How the chain is validated

Four instruments, none of which substitutes for another:

| | asserts | cannot see |
|---|---|---|
| unit suite | each link's logic in isolation | whether the links compose on a real target |
| `tools/pipeline_conformance.py` | "can it find THIS planted bug", end to end through the real autopilot, and that the bundle reproduces | plumbing it did not create: every fixture is a 2–8 KB file the gate compiled itself |
| `tools/real_corpus_gate.py` | PLUMBING HEALTH on real binaries and real libraries: nothing errored, nothing declined for OUR reason, a recorded crash produced a verified PoC, and REACH — how many of the library's doors were actually fuzzed (`DOOR`), since a library fuzzed through one of its six and through all six report the same execution count | whether the analysis is any good: **a target with no findings passes** |
| `tools/corpus_regression.py` (new 2026-10-15) | WHETHER THE FINDINGS ARE STILL THERE. Ground truth per real library — each known defect's CWE, its measured source site, the door it was reached by, and the verified PoC level it must reach — with zlib and bzip2 as precision controls and a REACH floor on every row | a defect nobody has recorded yet; it scores what the last measured round found |

The third exists because of the pattern this session made undeniable: **every new target exposed a
new defect, and not one was an analysis failure.** They were integration failures — a libtool
wrapper, a project typedef in a declaration, one `.cxx` file forcing C++ mode, a generated config
header, `examples/` code linked against absent symbols, a sanitizer exit code mistaken for a clean
run. Each was found by hand, one target at a time. The gate turns that into a table that runs
before an engagement rather than during one.

The fourth exists because the third **cannot see a regression in what we find.** "A target with no
findings passes" is the right contract for a plumbing gate and the wrong one for everything the
last two rounds bought: a harness planner that offers one door instead of six errors nowhere,
declines nothing, and reports a clean library; so does a build that goes back to resolving
`XML_Parse` from `-lexpat`. Every invariant stays green and the findings are gone.

Its three main verdicts are deliberately distinct, because they call for different work:

| verdict | means |
|---|---|
| `DEMONSTRATED` | the defect was found AND a verified PoC reproduces it — the only PASS |
| `IDENTIFIED` | the defect was found and nothing proved it. **Counts as a miss** |
| `MISS` | the defect was not found at all |

`IDENTIFIED` has its own word because "we identify, we don't demonstrate" is written into the notes
of three separate rounds, and a benchmark that scored it as a catch would launder exactly the
regression it exists to catch. Two further verdicts protect the measurement itself: a precision
control that produces a demonstrated memory-safety defect is a `FALSE-POSITIVE` (either a real new
find to record or a fabricated crash — the `gzopen(path)` one-argument call reported an ASan SEGV
in zlib on execution one, and this is the instrument that would have caught it), and a run whose
search was starved **or whose REACH collapsed** is `INVALID` rather than a pass. That last one is
the whole reason a findings-only benchmark could not do this job: zlib and bzip2 are *expected* to
run clean, so without a door floor a harness builder that stopped working entirely passes them.

Ground truth is deliberately not pinned tighter than the evidence supports. A site may be any of
several measured locations, because the exact line is a fact about which input arrived first and
not about the library — expat's namingBitmap shift reported `xmltok_impl.c:694` on 2026-10-14 and
`xmltok.c:147` on 2026-10-15, the same macro family through a different input. And a defect behind
a door the SECOND pass opens is `reach`-tier: scored and printed, never gated, because whether it
appears is the budget's decision. A `reach` entry is promoted to `anchor` when it holds across
runs; that is the only honest way to raise the bar.

The baseline it established, every library from its own tarball at a 600 s budget **[measured
2026-10-15]**:

| library | doors | executions | search | crashes | PoC | verdict |
|---|---|---|---|---|---|---|
| libtiff 4.0.3 | 6/6 | 256,336 | 232 s | 3 | L1 | **PASS** — 1/1 anchor demonstrated, 0/3 reach |
| expat 2.1.0 | 1/1 | 14,462 | 329 s | 1 | L1 | **PASS** — 1/1 anchor demonstrated |
| zlib 1.2.11 | 4/6 | 6,631,608 | 343 s | 0 | — | **PASS** — clean control, above its door floor |

## Cross-architecture breadth on real binaries, 2026-10-16

Every cross-architecture case this project had was a 2–8 KB file it compiled itself from one
planted-bug source, for the ISAs a cross compiler happens to package. That excludes MIPS
entirely on this host (Kali ships no `gcc-mips*-linux-gnu`), and it means the ISA ladder had
never met a real program: a stripped, statically linked megabyte of somebody else's code.

**The corpus.** 18 upstream busybox builds, 16 distinct arch/endianness/word-size combinations,
in `~/Downloads/multiarch/corpus` and picked up by `real_corpus_gate.default_corpus()`:

* busybox.net 1.21.1 prebuilt — arm (v4/v5/v6/v7), i486/i686, m68k, mips BE, mips64 BE, mipsel,
  powerpc BE, sh4, sparc BE, x86-64;
* busybox.net 1.31.0 defconfig-multiarch-musl — armv7m (static-PIE), armv8l, microblaze BE,
  powerpc64 BE, s390x, sh2 BE;
* Alpine 3.21 `busybox-static` 1.37.0 — aarch64, riscv64, ppc64le.

Plus `JonathanSalwan/binary-samples` (38 files) for front-end breadth: ia64, Alpha, hppa,
Haiku, Solaris/SPARC, fat Mach-O, PE for ARMv7-Thumb2.

**The first one failed the gate, and not for anything to do with MIPS.** busybox-mips-be ran

```
busybox-mips-be  yes  3,934  60.7  82s  WORK 9  DECL 7  ERR 1
  - stage errored: coverage_fuzz
  - oob_index declined, unclassified: out-of-bounds array-index probing is native x86-64 / ELF only
  - heap_trace declined, unclassified: custom-allocator tracing is native x86-64 / ELF only
  - heap_check declined, unclassified: heap check is native-arch only (target mips, host x86-64)
```

1. **`coverage_fuzz` ERRORED where it should have declined.** AFL++ qemu-mode needs an
   `afl-qemu-trace` built for the GUEST; this host has three (aarch64, arm, x86-64) and none for
   MIPS, and no distribution packages one. The stage raised, because a missing tracer had been
   classed as "an environment defect the operator fixes in ten minutes" — true on the native
   arch, false for a guest nobody ships. Meanwhile the orchestrator's fallback had already
   fuzzed the target 3,934 times, so the run reported a broken stage over a search that
   happened. Now: a foreign-arch target gets a decline naming the guest and the
   `CPU_TARGET=<arch>` build line; the native arch still raises.
2. **Four honest declines, none of them classifiable.** `classify_decline` is fed by substring,
   and the sentence was hand-written at each site: "native x86-64 / ELF only", "native-arch only
   (target mips, host x86-64)". Nothing matched, so the gate printed "unclassified" — which it
   treats as a defect — for four refusals that were each correct. Wording a classifier has to
   recognise cannot be hand-written per site, so `substrate.foreign_cpu_reason(arch, file_type,
   host, what)` is now the one sentence, used by `oob_index`, `heap_trace`, `heap_check`,
   `chain_primitive`, `extract_secrets` and the capability map's mirror of them.

### What the sweep could not find, and why: the dispatcher problem

Zero crashes on ten real binaries, and the reason is not that busybox is clean.
`cve_fingerprint` reads the banner and files 23 candidate CVEs against busybox 1.21.1 —
including CVE-2021-42374, an out-of-bounds read in the **unlzma** decompressor, and four
use-after-frees in **awk**. Nothing was demonstrated, because a multi-call binary is 345
programs behind one dispatcher and `busybox` with no function prints its usage and exits. The
campaign fuzzed the dispatcher.

`invocation.from_subcommands` could not see it, for reasons of SHAPE rather than of busybox: its
hint wants `usage: tool <command>` where busybox writes `Usage: busybox [function
[arguments]...]`, and its row parser wants one command per line with a description where a
multi-call binary prints a wrapped, comma-separated block of bare names. So:

* `multicall_names` reads the programs from the binary's own listing flag (`--list`, taken from
  the help text rather than invented) or from the block under `Currently defined functions:`;
* `rank_multicall` is an **allow-list by shape** — decompressors, archive readers, text/record
  parsers, hashes and dumpers — because among those 345 names are `reboot`, `mkfs.vfat`,
  `devmem`, `passwd` and the whole of service supervision, and a deny-list has to be complete to
  be safe. 345 → 55 allowed, deepest parser first;
* `multicall_doors` **verifies** each candidate by running it: `tar` with the input on stdin
  prints its usage, `unlzma` reads it, and nothing in a name says which. busybox 1.21.1 opens 14
  doors, every one a decompressor. A program that refuses every shape is dropped, not fuzzed;
* `multicall_seed` has the target make its own valid input: the image holding `unlzma` also
  holds `lzma`, so one execution produces a well-formed archive to mutate. A decompressor
  rejects random bytes at its header, which is how a campaign spends a whole budget at the
  front door;
* the autopilot takes the next `_MORE_MULTICALL_DOORS` doors as separate `fuzz` passes, which is
  the `libfuzzer` breadth pass again with no build to repeat.

`pipeline_conformance` gained `multicall_dispatch`: a fixture that prints a busybox-shaped help
text, lists `unlzma, reboot, cat`, and hides an unbounded `strcpy` behind `unlzma`. Without the
dispatch discovery that target is unfuzzable — every execution of the bare image prints its
usage — and `reboot` must never be invoked.

### The guard-page oracle nothing turns on

`memoracle.dislocator_preload` builds the environment that `LD_PRELOAD`s AFL++'s
`libdislocator.so` into a target, so that every allocation sits at the end of its own page with
an unmapped page just past it: a one-byte heap overflow faults immediately instead of corrupting
the next chunk, and a use-after-free faults instead of reading stale bytes. `batch_runner`
applies it in the forked child, scoped to the target and never to a sanitizer build.
`doctor` reports the library as present. **Nothing calls `dislocator_preload`, and nothing sets
`LYKOS_PRELOAD`** — `grep -rn LYKOS_PRELOAD core/` finds the reader and no writer, and doc 29
describes the oracle as something the operator turns on by hand.

This is the `libtokencap` finding again (audit 5), and it bites exactly where the chain is
weakest: a stripped, third-party, host-architecture binary with no source to instrument. busybox
1.21.1's own CVE list leads with an out-of-bounds READ, which is the defect class that does not
fault on its own — the campaign can execute the vulnerable path thousands of times and see
nothing.

Turning it on is not a one-line change, and the reason is the part worth writing down: a crash
found under a guard-page allocator reproduces only under one. The project's rule is that a
verified PoC reproduces, so the preload has to travel with the crash. It now does:

* `sandbox.guard_page_env` holds the preconditions in one place: never a sanitizer build (which
  already instruments every allocation), never a qemu guest (the preload object is
  host-architecture), and **never a statically linked binary**, because LD_PRELOAD is read by
  the dynamic loader and a static image ignores it completely. That last one is not a corner
  case: every busybox in the corpus above is static, as is most firmware, and tagging such a run
  as guarded would have put a false statement into the record;
* `sandbox.run` and `sandbox.run_batch` take `guard_page=` and record `+guardpage` in the
  isolation tag when it applied, which is the same field `replay_exe_for` already reads to tell
  a libFuzzer harness from the ingested binary;
* the campaign passes it at EVERY execution point: the batch runner, the per-exec fallback, the
  reproduction check and the minimizer. A crash found guarded and re-run unguarded does not
  reproduce and would be dropped as flaky, which is how an oracle turns into a regression;
* `build_poc` reads the tag and replays the same way, and `bundle` writes a `runner.sh` that
  exports the preload, lets the operator override the path with `LYKOS_GUARD_PAGE`, and says in
  plain words, when the library is absent on the replaying machine, that this defect is a heap
  error which does **not** fault on its own. The library is AFL++'s and is not ours to
  redistribute, so saying so is the honest alternative to shipping a reproducer that exits 0.

Measured on a fixture that reads 64 bytes past a 32-byte allocation: unguarded it exits 0 with
nothing to see, guarded it SIGSEGVs, through both `run` and `run_batch`
(`test_the_guard_page_turns_a_silent_heap_read_into_a_fault`). It does not apply to the busybox
corpus itself, for the static-linking reason above; where it applies is every dynamically linked
native binary, which is most of /usr/bin, the HTB corpus and every plain source build.

### What the doors found: busybox 1.21.1, an OOB read in the LZMA decoder

The A/B is the whole argument for the dispatcher work, on one target at one budget:

| busybox-x86_64, 600 s | execs | worked | crashes | verified PoC | demonstrated |
|---|---|---|---|---|---|
| fuzzing the image | 31,379 | 19 | 0 | — | 0 |
| fuzzing its programs | 22,090 | 25 | 8 | L1 | 1 |

All eight crashes came through the `lzcat` door — the LZMA decompressor, which is the codec
family busybox's own CVE list leads with. The campaign minimised one to **22 bytes**, and it
reproduces by hand outside the pipeline entirely:

```
$ cp busybox-x86_64 busybox && ./busybox lzcat < crash.bin ; echo $?
139
$ valgrind ./busybox lzcat < crash.bin
Invalid read of size 1
  at 0x48D899
Address 0x5dc12e14 is not stack'd, malloc'd or (recently) free'd
Process terminating with default action of signal 11 (SIGSEGV)
```

An out-of-bounds READ that faults, in a stripped static binary, found in ten minutes through a
door the engine discovered for itself. `cve_corroborate` links it to 16 of the 23 fingerprinted
CVEs as *corroboration* — "consistent with", never attribution, because nothing here maps a
fault location to a component — and the class matches CVE-2021-42374 (CWE-125 in the unlzma
decompressor, fixed in 1.34.0). The input is a mutated **bzip2** archive the target's own
`bzip2` produced, fed to the LZMA decoder: the self-seeding and the codec-family dedup both
mattered.

**And the same run exposed the next link.** `root_cause` reported

    input did not fault under the debugger via any of stdin, file, arg: gdb reported no crash

for a crash that is reproducible from a shell, because it stages the target as `target.bin`
— and busybox answers `applet not found` to all three channels under that name. So the defect
was filed as a generic CWE-119 rather than the CWE-125 valgrind names in one line, and L2 never
had a fault to work from. The filename is not a detail of the fuzz stage: every stage stages
the target itself, so `invocation.staged_name(ctx, target)` is now what `dynamic_run`,
`root_cause`, `mem_oracle`, `poc_primitive`, `synthesize_poc` and `build_exploit` use.

With the staging fixed, the same target re-run reaches one link further and stops at the next
one, honestly:

* `root_cause` now names the fault instead of missing it —
  `null-pointer-dereference (CWE-476): read through a NULL/near-NULL pointer (fault at 0x0);
  faulting instruction mov al,BYTE PTR [rdx+rax*1]`. That is an indexed byte load, which is the
  same thing `oob_index` reports independently as CWE-129, and it is worth noting that the class
  the chain files depends on WHICH crashing input got root-caused: one lands at 0, another (the
  22-byte one, under valgrind) at 0x5dc12e14. An unvalidated index, not a null pointer.
* `poc_primitive` declines: *"cyclic pattern did not fault via any of stdin, file, arg: no fatal
  signal"*, and `build_exploit` follows it. This is the next link and the reason is structural:
  L2 tests control by feeding a De Bruijn pattern, and a decompressor rejects that at its header
  before reaching any of its own logic. The crash needs a STRUCTURED input — the mutated archive
  the campaign already holds. The same argument the format-model seeding makes for the search
  applies to the control experiment.

So the honest state of this finding is: verified L1, named by root cause, corroborated against
16 fingerprinted CVEs, and not yet an L2 — with a specific, measured reason for the ceiling
rather than a silence.

### Seam 2 closed: a verdict for the address, with no sanitizer in sight

`oob_access_primitive` asks the right question — *does the attacker choose how far out of bounds
this goes?* — of a SANITIZER report, which exists only for a target we compiled. A stripped
third-party binary gives a signal, a faulting instruction, and the address the fault touched.
The ptrace helper has recorded that address (`fault_addr`, from `PTRACE_GETSIGINFO`) since it was
written; **nothing ever read it for a verdict**, which is why every real-corpus finding in this
project is an L1.

`primitive.address_primitive(observations)` asks the same question of that evidence: vary the
input, hold the faulting INSTRUCTION fixed, and watch the address. The honesty is in the
negatives, which are as much a result as the positive:

* **two different faulting instructions → None.** Those are two defects and their addresses are
  not comparable; inventing a primitive from them is the failure mode this family could have.
* **the same input faulting at two addresses → not input-controlled.** A heap pointer under
  ASLR, a pid, a clock. No claim is made.
* **a fixed address across every variant → denial of service, L1**, stated as such, with "in the
  first page, i.e. a null/near-null dereference" when that is where it lands.
* **a `ret` fault, or a PC outside executable memory → None**, because that is instruction-pointer
  control and the cyclic experiment is the instrument for it. Measured: without this guard the
  stack-overflow fixture came back as an "address-control read", relabelling a control-flow
  hijack as a read primitive.
* native only, because `fault_addr` comes from ptrace's siginfo and a qemu gdbstub capture has
  registers without it.

Sibling crashes are folded in for free: the campaign that produced one input usually produced
several, and two crashes faulting at one instruction with two addresses answer the question
without varying anything.

**The first real answer it gave was a negative, and it corrected us.** On busybox's `lzcat`
crash — 16 single-byte variants plus 6 sibling crashes, 22 observations, one faulting
instruction — every fault lands at **0x0**. So that defect is a null-pointer read: a denial of
service, exactly as `root_cause` classified it from a single observation, and NOT the
index-controlled read the earlier write-up in this document supposed. (Valgrind's non-zero
address for the same input is valgrind's own allocator moving the layout, not evidence of input
control.) The verdict is now a measurement rather than a guess in either direction.

The fixture that proves the positive half is `test_an_indexed_read_is_an_address_primitive_not_a_dos`:
a header-gated parser (so a De Bruijn pattern never reaches the defect), an unvalidated index,
no `win()`, and a READ — the three properties that together produced every L1 ceiling in the
real corpus. It reaches **L2**, naming the input byte that moves the address and the stride it
moves by.
