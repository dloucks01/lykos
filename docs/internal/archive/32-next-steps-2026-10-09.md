## How to measure, and why the gate cannot

`tools/breadth_probe.py` points the real autopilot at ordinary binaries and records the **work** —
baseline execution, executions and rate, where the time went, which stages were reached, what each
declining stage said. There is no pass mark; the output is a table you read.

`tools/pipeline_conformance.py` cannot answer the same question, and the reason is structural
rather than a missing case: every fixture is a 2–8 KB binary the gate compiled itself (`-O0
-no-pie`) with a planted defect reachable in the first few hundred inputs, and the harness stops
the moment the criterion is met. It measures *"can it find this bug"*; the probe measures *"how
much of the budget reached the target"*, and only the second predicts behaviour on software nobody
prepared for us. **Use both. Neither substitutes for the other.**

Reference throughput, measured not assumed (`analyze/budget.py` carries the table): native **174
exec/s** batched / **46/s** unbatched, JVM ~36/s, `.pyc` ~19/s, wasm ~11/s, CLR ~8/s, Wine ~1/s.

## Open — in priority order

### 1. Re-measure the breadth sample post-fix (do this first, it is cheap)

The budget work was verified by re-running **one** binary. The original four-binary sample has not
been re-measured, and the one that scored zero executions is the interesting case:

| | executions, pre-fix, 420 s |
|---|---|
| `/usr/bin/cat` | 1,511 |
| `/usr/bin/xxd` | 2,756 |
| `/usr/bin/readelf` | 1,473 |
| `/usr/bin/jpegtran` | **0** |

```
python3 tools/breadth_probe.py --budget 420 --json /tmp/post.json \
    /usr/bin/cat /usr/bin/xxd /usr/bin/readelf /usr/bin/jpegtran
```

Then widen it: `python3 tools/breadth_probe.py -n 12` (random `/usr/bin` sample). Anything with a
`NO-RUN` baseline or a zero execution count is the next bug, and the scorecard says which stage
ate the clock. Keep the runs **serial** — concurrent autopilots overload the engine and produce
false negatives.

### 2. Seed synthesis per detected format — the largest remaining multiplier

A format parser with no operator-supplied seeds is still close to unfuzzable: the campaign spends
its whole slice being rejected by the first length/magic check. Nothing synthesises a *minimal
valid input* from the format the pipeline already detected. The pieces exist and are not connected:
`fuzz/grammar.py::from_spec` bridges a flat format spec to a flat grammar, `fuzz/cmpdict.py` mines
comparison constants, and triage already names the format. What is missing is a
`synthesize_seed(spec) -> bytes` that emits one structurally valid specimen (magic + a coherent
header + one minimal record) and seeds the campaign with it when the operator supplied none.

This is the difference between "we fuzzed a decoder for 80 s" and "we fuzzed a decoder". Highest
expected yield of anything in this list.

### 3. Case-level stages still sit outside the budget

`analyze/budget.py` divides the **per-target** clock. The four case-level stages keep their
registered timeouts: `link_case`, `ipc_model`, `cross_taint` (no explicit timeout → the queue
default of **3600 s**, `jobs/config.py:28`) and `whole_system` (**registered at 3600 s**,
`analyze/link/whole_system.py:181`). On a multi-binary case any one of them can still outlast the
whole run, which is exactly the defect the budget fixed per target. Fix shape: a `CaseBudget`
scoped to the case, sliced across the case-level stages the same way, with the per-target budgets
drawn from what remains.

### 4. `build_exploit` is the dearest stage on a crashless target

Final scorecard for `/usr/bin/xxd`: `build_exploit 82.9 s, fuzz 81.1 s, directed_fuzz 72.7 s`. The
most expensive stage in the run **produced nothing**, because there was no crash and no reachable
leak oracle for it to weaponize. It is bounded now, so this is cost rather than a hang — but the
right fix is a cheap precondition check: with no crash, no primitive and no leak oracle on the
target, decline in milliseconds instead of spending a phase's share.

Note for whoever picks this up: **do not "fix" this by moving the stage later in the pass.** Its
early slot is itself an earlier fix — the end-of-pass slot was never reached — and the comment at
the call site says so. The lever is the precondition and the `want=` at the call site.

### 5. Per-architecture depth — 13 ISAs, one bug class

The arch gate (`core/lykos/eval/archgate.py`) has **one** fixture source — a 64-byte stack
`memcpy` — compiled for 13 ISAs. Every row therefore measures the same bug class, so "aarch64:
L3" means "a stack overflow reaches L3 on aarch64", not "aarch64 is covered". Three concrete
pieces, in order:

a. **Cross-arch heap checking is unattempted, not blocked.** `heap_check` never runs for a foreign
   CPU, and the reason recorded in the code is a presumption. Measured otherwise: a cross-built
   shim detects an aarch64 use-after-free under qemu today, in minutes. Start here — it is the
   cheapest real capability gain in this section.

b. **Frame-layout-aware reachability.** On AArch64 `stp x29, x30, [sp, #-N]!` saves the link
   register *below* the locals, so an upward overflow from a buffer in `main` never reaches it:
   measured clean at 60 KB where x86-64 faults at 400 bytes. This generalises the SPARC `%i7`
   note already in the matrix. The tool should **state** "on this ISA the saved return address is
   below this buffer, so this overflow cannot redirect control flow" instead of silently finding
   nothing and reporting a clean result.

c. **A per-arch bug-class matrix** with per-arch expectations. Per-architecture bug expectations
   cannot be copied across ISAs — (b) is the proof — so the matrix needs its own expected level
   per (arch × bug class), not one column stretched across 13 rows.

### 6. The one deliberate gate gap

`off_by_one` is the single `KNOWN GAP` case in the conformance gate
(`tools/pipeline_conformance.py:867`): two bytes past a 64-byte buffer land in padding or the saved
frame pointer and do not fault, so there is no crash to find, and no static detector files
CWE-193. Closing it needs either a static single-byte-overflow detector or a layout-aware oracle
that flags the write without a fault — which is the same machinery as 5(b). `grep "KNOWN GAP"` is
the authoritative list; it should stay one line long.

### 7. Weaponization ceiling, honestly stated

The leak-centric architecture landed (shared interaction model in `analyze/interaction.py`, cached
leak recon, PIE+canary → ret2win and → ret2libc, format `%n` onto a saved return under Full RELRO,
crawled-menu-driven heap FSOP). What remains open:

- a **leak-free PIE target with no in-binary `win()` and no forking server** — BROP needs one or
  the other; with neither there is no reachable path today, and the honest output is the
  demonstrated primitive plus the reason.
- **socket-offset autodiscovery** for the networked weaponizers.
- **create-as-write** (a heap target with an allocate path but no edit path) and the OOB-index
  write as first-class heap primitives.

## Process notes worth keeping

- **Two of the bugs in `81142f3` were introduced by the fix itself** and were caught only by
  re-measuring the same binary, not by the suite. (a) Handing one number to both the stage, as its
  campaign length, and the worker, as its kill deadline, killed every campaign at the instant it
  would have returned — the work was done and the summary discarded. The worker's deadline is now
  `want * 1.2 + 10 s`. (b) A flat `+30 s` orchestrator grace became the dominant term on a short
  budget; it is now proportional, `min(15, max(3, slice * 0.25))`. **Re-measure after a timing
  change; the suite cannot see this class of bug.**
- **Unifying a duplicated table is only safe when the duplicates answered the same question.**
  Round 2 collapsed two CWE lists into one and so kept a DoS-grade CWE-476 on a confirmed hijack;
  `db/models.py` now carries `MEMORY_CORRUPTION_CWES` (a severity floor) and
  `OUTRANKS_PRIMITIVE_CWES` (a keep-list) separately, because they are different questions.
- **A missing `DynResult` row means "no crash recorded", not "no execution".** Read the scorecard's
  execution counts, never the crash table, to answer "did it run".
- Full gate runs are slow; prefer a named subset — `python3 tools/pipeline_conformance.py
  heap_uaf_read clean_no_bug argv_overflow env_overflow` — and keep it serial.
