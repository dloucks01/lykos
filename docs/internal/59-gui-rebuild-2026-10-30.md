# 59 — Ground-up GUI rebuild around the new PoC-engine model (2026-10-30)

Operator decision: rebuild the web GUI from scratch to fit the doc-58 model, reduce LOC, and
**lose no capability we will need** (firm full-CLI-parity requirement, memory `webgui-cli-parity`).
Current GUI: ~5,800 lines across app.js (1680), components.js (2613, ~55 components), autopilot.js
(603), util.js (554), api.js (220). This doc is the capability guardrail + the new architecture +
the build order. Nothing here ships until a capability it lists is either re-ported or explicitly
retired with reason.

## The new model the GUI must express (doc 58)
Per finding: a **validated PoC deliverable** — the lightweight payload + a few-line repro + the
soundness argument + a **provenance** badge (`constructed` = sound, no-exec; `detonated` = oracle
fired) — OR an **honest dead-end** that says what blocks it and, when execution is needed, a
**missing-deps / environment manifest** (which libs/configs/args to supply). The confirmation ladder
is candidate → corroborated → confirmed (constructed) → poc-backed (detonated). "Prove it out —
directed plan" (telling the operator what they could run) is RETIRED: the tool does it or says
honestly why it cannot.

## Guiding principle (operator, 2026-10-30): keep ONLY what we will need
Do not re-port for parity's sake. Build what the new model needs; carry a capability forward only
when a real need for it shows up; **DROP anything we don't need.** "Hard to determine atm" is handled
structurally: the OLD GUI stays intact as the reference/fallback until the rebuild is complete, so
NOT porting something loses nothing — we revisit it the moment a need appears. So the inventory below
has three live buckets: NEED (port now), DEFER (leave in the old code, port only if a need appears),
DROP (retired — do not port). This supersedes blanket "KEEP for parity"; it refines, not revokes,
`webgui-cli-parity` — parity with what the tool actually needs going forward, not with legacy surface.

## API surface to preserve (api.js — the parity contract)
cases, cases/{id}, cases/{id}/targets, targets/{id} (+delete), targets/{id}/{advice,source,
capabilities,findings,functions,callgraph,strings,dynresults,pocs}, functions/{id}, findings/{id}
(+curation GET/POST), cases/{id}/curation, targets/{id}/{invocation,replay}, runs/{id}(+output,
cancel), cases/{id}/{runs,findings,coverage,timing,systemmap,verifications}, version/health, the
event stream. The rebuild consumes the SAME endpoints (no backend API churn) + reads poc.provenance.

## New architecture (smaller by construction)
- Plain ES modules + the existing tiny html`` tagged-template (util.js) — keep the no-build,
  air-gap-friendly stack; do NOT add a framework.
- Three layers: `api.js` (unchanged endpoints) → a thin `store` (case/target/run state + event
  stream) → view modules. One view module per workbench tab, each small and independent.
- The finding → PocDeliverable path is the spine; everything else hangs off the same target state.
- Target: materially fewer lines than 5,800 by dropping the retired framing and de-duplicating the
  verdict/ladder/poc rendering into the 3 NEW shared blocks — WITHOUT dropping a KEEP capability.

## Build order (incremental, each shippable + checked against the inventory)
1. Skeleton: shell, nav, store, event stream, DropZone+upload, BuildFoot — app loads a case.
2. The spine: target view + FindingCard(REMODEL) + PocDeliverable + ConfirmationLadder + EvidenceModal.
3. TargetEnvPreflight (new) + honest dead-end rendering.
4. Re-port KEEP analysis tabs: Code/Disasm/Functions/CallGraph/Strings/Diff/Crashes.
5. Re-port run/process + honesty: RunHeader/Scorecard/SignalsStrip/ProgressLog/Console/AttemptLogs.
6. Re-port coverage/fuzz/yield: Coverage/FuzzHealth/Ledger/Seeds/Timing + FuzzConsole live window.
7. Re-port case/multi-binary: CaseOverview/EngagementMap/SystemMap/VerdictStrip + Curation.
8. Infra: Doctor/Selftest/Unavailable. Then delete the old app.

Each step ends by ticking the inventory; the old GUI stays until step 8 so nothing is lost mid-flight.
This is a multi-session build.
