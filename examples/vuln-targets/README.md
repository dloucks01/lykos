# Vulnerable targets — real third-party code, many architectures

The corpus next door (`../re-corpus`) exercises triage and decompilation: busybox, ripgrep,
packed and stripped variants. Nothing in it is vulnerable, so none of it drives the part of
the pipeline that matters most — **detect → fuzz → crash → root cause → PoC**. Until now that
chain was proven on two programs (jhead, ncompress), both x86-64, and the architecture gate
compiled a *synthetic* program for everything else.

These are real programs with real bugs, built for every toolchain on the machine.

```sh
./fetch_build.sh     # downloads pinned sources (sha256-checked), builds into bin/
```

Binaries are not committed (reproducible); `bin/manifest.tsv` is.

## What's here

| target | format | why |
|---|---|---|
| **jhead 3.04** × 12 ISAs | JPEG/EXIF | CWE-125 out-of-bounds read, reproduces on every ISA |
| **giflib 5.1.4** `gif2rgb` | GIF | negative case: a real parser the chain should run clean on |
| **Info-ZIP 6.0** `unzip` | ZIP | a large real parser (3,705 blocks) for the ZIP model |
| **ncompress 4.2.4.4** (CVE reverted) | argv | CWE-121 stack overflow; the only target here that reaches **L2** |

### The reverted CVE

`ncompress_x86-64_cve` is upstream 4.2.4.4 with the CVE-2001-1413 length check removed --
one `if` around the `strcpy` of an argv pathname into a 1024-byte stack buffer. Upstream
carries the fix and the historical vulnerable release is no longer on the mirrors, so the
build script reverts it from the pinned tarball and names the binary `_cve` to keep that
visible. It is test material: never installed, never redistributed.

It is here because every other target's bug is an out-of-bounds *read*, which cannot give
instruction-pointer control. This one does: the ladder reaches **L2, confirmed at offset
1048**, and the release gate asserts it. L3 is not reached on any real target yet -- the
platform reports precisely why ("no win function, and no pop-rdi gadget + /bin/sh +
system@plt for a ROP chain") rather than failing quietly.

`x86` (32-bit) is skipped unless gcc multilib is installed; every other toolchain absence is
reported and skipped, the same rule the arch gate uses.

## The jhead bug, and why the inputs are committed

`ProcessGpsInfo` reads `count` bytes from `base + offset` for a GPS directory entry, and the
bounds check adds those two together **in 32 bits**. A pair that wraps passes the check while
the offset still points far outside the segment: `0x00ffffff + 0xff000002` is 1. Neither half
does it alone — a huge count is refused, a far offset is refused.

- `inputs/jhead-ok.jpg` — 215 bytes, parses cleanly (`Resolution : 8 x 8`, GPS latitude)
- `inputs/jhead-crash.jpg` — the same file with one entry's `count`/`value` replaced by a
  wrapping pair. Faults on all 12 ISAs.

Both are **generated by lykos's own JPEG model**, not captured from a fuzzer — `seed_for_name`
produces the first, and driving one declared offset/size pair produces the second. They are
committed because they are the cross-architecture regression fixture: the crasher must fault
and the seed must parse, on every ISA, which is what `fetch_build.sh` asserts at the end.

## Using them

```sh
python3 -m lykos ingest examples/vuln-targets/bin/jhead_aarch64 --case x
```

Nothing needs to be told the format or handed a seed: `detect_cwe` reads the binary's strings,
picks the model, and generates a seed that the target's own parser accepts.
